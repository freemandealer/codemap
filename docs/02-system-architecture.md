# 02 · 概要设计

## 1. 总体结构

CodeMap 分为生成端与阅读端。生成端的 Agent 负责理解和叙事，程序负责可检查的提取、验证、布局和打包。阅读端是静态浏览器应用，只消费已经生成的数据，不读本地仓库、不访问模型。

查看[交互式架构图](diagrams/codemap-system.html)。主路径为：

```text
代码快照 + 阅读目标
        ↓
Code Agent 按 Skill 阅读、选择证据、构建语义地图
        ↓
map.codemap.json（可编辑的生成源）
        ↓
结构检查 → 引用与源码核验 → 语义审阅
        ↓
确定性布局编译 → 索引与投影准备 → HTML 打包
        ↓
map.html（离线阅读 / 静态站点 / iframe）
```

语义审阅由生成端完成，不声称机器校验可以证明解释正确。Archify 已采用结构化输入、校验和 HTML 交付的分离方式；这里借鉴此边界，自行设计代码地图协议和多尺度阅读器。[Archify 官方说明](https://github.com/tt-a1i/archify)

## 2. 模块职责

| 模块 | 输入 → 输出 | 责任与边界 |
| --- | --- | --- |
| Skill | 用户问题 + 仓库 → 生成计划与 IR | 指导检索、阅读、分层、审阅；不生成任意 JS |
| SnapshotReader | 目录与选择范围 → 文件指纹、文本片段 | 只读提取、标准化路径、记录快照；不执行目标代码 |
| MapAuthor | 代码证据 → CodeMap IR | Agent 构建解释、实体、原子关系、讲解树 |
| Validator | IR + 可用快照 → 诊断 | JSON 结构、跨表引用、树不变量、源码一致性、预算 |
| LayoutCompiler | 合法 IR + 固定配置 → Scene | 分配区域、局部坐标、节点顺序、端口和空间索引 |
| Packager | Scene + IR + 固定阅读器 → HTML | 内嵌依赖、转义、证据裁剪、生成构建收据，原子替换 |
| Viewer | HTML 内嵌数据 + 手势 → 显示状态 | 相机、语义投影、连线、搜索、面包屑、详情、大纲 |
| StaticHost | 交付的 HTML → URL | 用户已有网站/静态托管；首版不建设服务端 |

所有模块都围绕一个明确的输入版本。不会通过“浏览时再问 LLM”补全缺失节点。

## 3. 三种数据必须分开

1. **CodeMap IR**：目标、事实实体、讲解节点、原子关系、源码与证据。它是可长期保存的语义源。
2. **Compiled Scene**：确定的区域和坐标、边路由辅助索引、文本测量结果、ID 索引。它可以从 IR 重建。
3. **ViewState**：当前相机、展开集合、选中对象、过滤和返回历史。它属于读者，不修改 IR。

Agent 不手写像素坐标。布局程序不能补充语义事实。查看器不能在缩放时推断新的调用关系。这三条边界使输出可测试，也便于未来更换模型或渲染技术。

## 4. 核心模型

实体图表示代码“有哪些对象、它们如何关联”，允许环、递归、共享和多对多。讲解树表示“为了这个问题应该如何逐步理解”，每个讲解节点只有一个父节点，树内允许多个节点引用同一实体。

每个实体指定唯一的 `canonicalNodeId`，作为关系投影的默认起点。其他讲解引用属于别名，通过详情定位到规范位置，首版不为每个别名复制一套连线。这样既允许复用，又避免关系数量膨胀。

节点深度是树的结构属性，显示密度是视口状态。两者不等同：同一画面中聚焦模块可以显示函数，邻近模块仍可显示摘要。具体可见前沿和端点投影算法见 04。

## 5. 布局策略

首版使用确定性的递归区域布局，按逻辑父子关系划分嵌套区域。Agent 只提供有限提示：同层顺序、主路径、分支角色、重要性。编译器负责大小和位置。

- 概览层采用有序网格/分区，同层模块保持稳定方位。
- 顺序步骤采用从上到下的轨道；分支放在相邻列，循环显示回边。
- 子区域在父节点的内容矩形内布局，标题和边界端口保留独立空间。
- 固定布局版本、排序规则、字体度量与数值舍入；同一输入不运行随机力导向。
- 缩放只切换表现和可见集合，不能因节点变多重新洗牌整个地图。

跨父区连线经过共同祖先的通道；先保证端点和方向正确，再优化交叉。路由无法在预算内清晰展示时，聚合/突出选中关系并提供列表，不声称能自动产生任意规模的完美蓝图。

递归布局可能产生极小的叶子区域。Scene 使用父级局部坐标；超深路径通过焦点坐标重基准保持浮点精度。数据层不固定层数，v0.1 对超过 32 层的输入给出预算错误，要求减少无意义层次；这属于资源保护，不是产品只能有五层。

## 6. 建议技术基线

以下为待原型验证的工程决策，不是已经创建的依赖清单。

| 部分 | v0.1 建议 | 选择依据 / 替换条件 |
| --- | --- | --- |
| 数据与核心算法 | TypeScript；JSON Schema 2020-12 | CLI 与浏览器共享类型和投影算法 |
| CLI/构建 | Node.js LTS；固定依赖锁文件 | 便于随 Skill 分发构建好的执行文件；具体最低版本由实现验证 |
| UI | 轻量 DOM 组件，独立状态容器 | 控件与代码文本适合 DOM；不需要完整应用框架才能开始 |
| 画布 | SVG 连线 + DOM 卡片，统一相机变换 | 文本选择、键盘和证据面板容易实现 |
| 手势 | 封装 d3-zoom 或等价适配层 | 官方接口覆盖平移、滚轮、触摸及程序控制；语义 LOD 由 CodeMap 实现 |
| 自动布局 | 自有有序区域/步骤布局 | 稳定递归容器优先；复杂局部图再评估布局库 |
| 索引 | 预构建 ID/祖先/文本/区域索引 | 中小地图不引入搜索服务或图数据库 |
| 测试 | 单元/性质测试 + 浏览器端到端 | 验证投影守恒、手势、离线、内嵌与证据 |

d3-zoom 是手势与相机能力来源，不能自动生成抽象层次或拆分语义边。[D3 官方文档](https://d3js.org/d3-zoom)

首版暂不采用 WebGL：文本可访问性、离线体积和代码阅读优先。若实际基准超过同屏预算仍不能满足性能，保留统一 Scene 与投影接口，将边绘制切换到 Canvas；不要在数据契约中耦合 SVG 元素。

## 7. 运行与构建接口（拟定）

```ts
validateMap(map, snapshotReader?): Diagnostic[]
compileMap(map, compilerOptions): CompiledScene
projectView(scene, viewState): VisibleScene
packageHtml(map, scene, runtimeBundle): Artifact
```

`compileMap` 是纯计算，不访问模型或网络。源码核验在生成机上完成，发布文件中保留核验状态与材料；接收者只拿到 HTML 时可检查内嵌文本，但不能凭空证明私有仓库确实存在。

构建收据记录 IR 指纹、编译器与阅读器版本、输出指纹、校验摘要。可重复性承诺限定于**同一 IR、构建产物和选项**；不同模型重新生成不保证相同结果。运行时性能数据和构建时间放在外部收据，不进入可复现 HTML 的字节输入。

## 8. 未来网站如何接入

将来可添加 `AnalysisJob → Agent/模型适配 → CodeMap IR` 的生成服务，后续编译与阅读链路继续复用。网站需要单独设计上传隔离、密钥管理、资源配额、计费、清理和任务生命周期；本期只要求 IR 与生成宿主解耦，不提前实现这些模块。

所谓兼容 API 是未来适配层要求，不意味着所有服务端都支持相同工具调用、结构化输出或上下文长度。届时按能力检测和契约测试设计，模型凭据永不进入地图文件。
