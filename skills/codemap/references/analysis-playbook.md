# 证据驱动的分析

先确定阅读视角。流程问题提取入口、关注状态、成功条件与失败结果；架构问题提取子系统边界、职责、接口、共享对象与关键依赖，结合 [架构组织方法](architecture-playbook.md) 分析。先 `rg` 搜索，再逐段读取相关代码；记录已读文件集合。默认读者了解语言，不了解模块。

对主路径或模块协作建立台账：实体、文件范围、条件、输入输出、状态变化、错误分支、资源所有权和调用绑定。架构取证不能只覆盖一个入口；核对范围内关键模块的接口和联系。调用点与绑定表可能在不同文件；证据必须来自同一快照。无法确定的宏、配置或动态目标进入 assumptions/openQuestions，不猜成确定调用。

流程可从语句总结步骤与函数，再把协作总结为机制与职责；架构先提出职责分区，再以接口、类型、绑定和实现验证分区。两者都要反向问每个父节点“孩子是否足以支撑这个说明”。跨文件职责可以同属一个节点，共享函数可以有多个讲解引用，但实体与原子关系只登记一份。

使用程序取源码片段。按真实行区间划分保留/省略，保留异常、释放和返回语义。长函数可以由不同节点解释不同区间，不拼成貌似连续的完整函数。源注释保持原文，作者解释放在 summary/details。

到用户问题已经得到回答、外部边界明确、或预算耗尽时停止；注明哪些是未读、哪些是不适用。范围过大时收窄问题：流程保留能追到底的路径；架构保留范围内的职责与关键联系，再给代表性深入路径。避免“全库覆盖率”；coverage 只描述本问题的路径或模块协作清单。
