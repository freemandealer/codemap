# 按架构组织地图

架构图回答“由哪些部分组成、各自负责什么、通过什么联系”，主视角写为 `scope.viewpoint: "architecture"`。先定模块边界与关键联系，再选择代表性实现深入；不要因为最先找到一个入口，就把整个系统压成该入口的一条调用链。

## 从职责建立层次

- 根说明子系统目标与范围。下一层按职责、接口边界、资源所有权或实现家族建立 `module`；名称应能独立成立，例如“请求编排”“存储后端”“缓存管理”。一个模块可以跨文件，一个文件也可以包含多个职责。
- 模块摘要交代职责、对外接口和关键约束；可用 `details.inputs/outputs/invariants` 表达协作契约。子层按问题选择子模块、机制、数据类型或函数，不要求每个模块同深度。
- 区分接口与实现。共享对象放在有依据的规范位置，其他模块通过关系或别名引用。关系可以成环、多对多或跨层；讲解树保持单父节点。
- 在需要解释实现时，再进入模块内的函数、局部步骤与原始代码。只有有真实控制顺序的局部逻辑才使用 `flows`，不要为连接顶层模块编造 `next` 边。

## 用实体事实连接模块

为每个关键联系记录两端实体、接口/对象、关系类型、条件和证据。优先复用 `call`、`dispatch`、`read`、`write`、`ownership`、`dependency` 等现有类型；`dependency` 方向为依赖方 → 被依赖方。指针引用不自动等于资源所有权，静态依赖不自动等于一次运行时调用。

原子关系挂到实体的规范节点；折叠时由阅读器投影到模块边界，展开后定位具体实现。接口证据只支持接口，就连到接口，不猜具体目标。动态分派需要调用点和绑定证据；条件写入 `condition`。一个联系对应同一事实时只登记一次，不额外复制“模块边”来增加粗线数量。

`order` 只决定稳定摆放，`primaryPath` 只建议先读什么；二者都不表达执行先后。架构图的导读可以是“总览 → 一个模块 → 对外接口 → 实现 → 源码”。完整性按关键模块及联系检查，不能只因这条导读走通就宣称系统全部覆盖；沿用 `coverage` 字段列出已解释、部分解释和排除的职责/协作。

## 提示词对照

| 提示词 | 应生成的结构 |
| --- | --- |
| “一次打开请求怎样完成？失败如何释放资源？” | 流程为主，围绕条件、分派、结果和清理展开 |
| “打开请求涉及哪些模块？接口如何分工？” | 架构为主，围绕职责和接口组织；“请求”一词不意味着必须流程化 |
| “按架构理解 Linux I/O，关注 VFS、具体 FS、Block I/O、Driver 的联系。” | 以这些名称作为候选职责分区，读取指定版本后确认边界和联系；不能直接把四个框排成必经顺序 |
| “先展示 I/O 总体架构，再展开一次读取。” | 架构总览为主，局部展开所选请求；不要把所有模块都拆成该请求的步骤 |
| “不要架构总览，只追这个函数如何返回。” | 尊重明确选择，采用流程视角 |

Linux 的名称示例是阅读目标，不是已核验的实现结论。必须固定真实仓库版本、配置与分析范围；没有相关源码时说明缺口。不能用教学例子补成 Linux 事实，也不能把未读取的模块写成没有依赖。

## 对照样例与审阅

`examples/minifs/architecture.codemap.json` 与流程样例使用同一源文件和快照。架构样例按打开接口、后端协议与实现、文件槽位、名称空间分组，增加接口依赖和共享对象的读写联系；打开函数的步骤仍保留在模块内部。

审阅时检查：只看概览能否说清各模块职责和联系；连线是否说明具体接口、条件或对象；是否把目录、时间阶段或别名误当成独立模块；展开后原子关系是否仍对应同一份证据。预算不够时收窄子系统，保留选定范围内的联系和明确边界。
